# Proposed hybrid: stronger discovery, one workbench

This is a proposal, not an active replacement for the current skills or agent instructions. The [work README](README.md) owns the acceptance criteria and execution checklist. This document fixes the intended file layout before trying skills that would otherwise create competing artifacts.

## Problem and decision

The current [`planning-first`](../../../skills/planning-first/SKILL.md) forces two question rounds and separate permission to save a plan and to build. That structure is too rigid for the user's current workflow. Matt Pocock's [grilling](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/productivity/grilling/SKILL.md) explores a dependent decision tree more effectively, while his [domain modeling](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/domain-modeling/SKILL.md) separates enduring terms and decisions from task notes. His engineering flow assumes an issue tracker, root `CONTEXT.md`, `docs/adr/`, and in places a `Skill` tool or automatic commits. Adopting that flow unchanged would undermine the existing workbench and delivery rules.

**Proposed direction:** Keep [`todo-manager`](../../../skills/todo-manager/SKILL.md) and [`ship`](../../../skills/ship/SKILL.md) as the lifecycle backbone. Try the upstream `grilling` primitive first. Maintain locally adapted skills for repo-aware discovery, optional spec synthesis, and domain documentation. Borrow the useful visual evidence from the upstream `pr` skill inside the existing `ship` PR-writing flow. Decide whether to adapt `to-tickets` only after a real multi-slice trial. Pin unchanged upstream reference skills where their instructions are portable and do not compete for artifact ownership.

This is a **documentation-first contract, trial second**, rather than pinning several production skills and sorting out the files later. Do not create an issue tracker, glossary, ADR directory, spec file, or ticket directory merely to make a skill happy.

## Artifact contract

The paths below are defaults for a project that already uses this workbench or explicitly adopts it. Existing authoritative docs and legacy task locations take precedence until a separate migration is authorized. Create optional files only when their content exists. A repo may use a different established documentation path, recorded once in its agent entry point; adapters must follow it rather than silently building this layout alongside it.

| Artifact | Owner and purpose | Not for |
| --- | --- | --- |
| `AGENTS.md` or the existing agent entry point | Short, cross-agent pointer to the live task queue, domain glossary, decisions, and applicable skills; project-specific constraints | A second task list, glossary, or transcript |
| `todo/TODO.md` | One live P1–P5 priority index; links substantial work records | Triage state labels, full specs, detailed duplicate checklists |
| `todo/work/<effort>/README.md` | Stable record for purpose, status, ownership, acceptance criteria, one detailed execution checklist, decisions specific to the effort, and links | Enduring domain definitions or a second changelog |
| `todo/work/<effort>/plan.md` | Optional current design and consequential alternatives when they no longer fit in the README | Another execution checklist or a general project manual |
| `todo/work/<effort>/spec.md` | Optional detailed behavioral contract synthesized from an agreed discussion for substantial or multi-session builds | A required file for small work, another checkbox list, an automatic GitHub issue |
| `todo/work/<effort>/research.md`, `validation.md`, `assets/` | Evidence when useful, linked from the work README | Automatic per-session output or unlinked scratch |
| `docs/domain/README.md` | A concise glossary of domain-specific terms, preferred names, and avoided synonyms; also indexes any genuine subdomains | Implementation steps, status, roadmap, task acceptance criteria |
| `docs/domain/<context>.md` | Optional glossary for a genuine bounded context when one glossary stops being usable; indexed by `docs/domain/README.md` | One file per feature or per work record |
| `docs/adr/NNNN-<decision>.md` | Rare, enduring, surprising, hard-to-reverse tradeoffs; linked from the work record and relevant project docs | Every local implementation choice or copied plan history |
| Existing maintained project docs | Current operational and architectural reference, separate from work history | Replacing the task index |
| `CHANGELOG.md`, Git, PRs, `todo/DONE.md` | Release notes, verified delivery/history, and navigation, respectively | Claims inferred from a checked task |

For a project with a single domain, `docs/domain/README.md` holds the glossary directly; there is no obligatory tree of context files. The first resolved domain term justifies creating it. If the project already has a `CONTEXT.md` or another glossary, point to and use that instead of duplicating it. Likewise, `docs/adr/` is a lazy default, not a request to relocate existing decisions. A repository without a task workbench keeps its existing tracker until it explicitly adopts or migrates one.

**One source of truth at each resolution:** The work README owns the authoritative checklist and acceptance criteria. A spec elaborates behavior, examples, testing seams, and scope, and references the README criteria rather than maintaining checked copies. An ADR records the durable decision and links its original work record for evidence. The work record links the ADR as the current authority and keeps only effort-specific context. A glossary defines terms; an ADR explains a choice; a plan describes a proposed approach. Neither the glossary nor an old work record silently becomes a standing instruction.

**Promotion rule:** While grilling, note tentative terms and decisions in conversation. On an authorized write, put effort-specific decisions in the work README or plan. Add a term to the maintained glossary when its meaning is settled and needed beyond this effort. Offer an ADR only if the choice is hard to reverse, surprising without context, and the product of a real tradeoff. Existing approved documents may be updated as the user works; a read-only discussion never writes to them. The agent entry point should tell agents to read the relevant glossary and decisions when planning, naming, testing, or reviewing that domain.

### Example, not scaffolding to create now

```text
AGENTS.md
CHANGELOG.md
docs/
  domain/README.md             # only after a term needs a shared definition
  adr/0001-<decision>.md       # only after a qualifying decision
todo/
  README.md
  TODO.md
  DONE.md
  work/<effort>/
    README.md                  # the effort's entry point and only checklist
    plan.md                    # if design needs room
    spec.md                    # if a durable behavioral contract needs room
```

No `.scratch/<feature>/issues/` tree, parallel `docs/agents/issue-tracker.md`, root `CONTEXT.md`, or hosted issues are created by the default hybrid. If a repo already uses hosted issues, an issue URL can be linked from the work README. Decide explicitly which location owns status and acceptance criteria before mirroring anything across systems.

## Process contract

1. **Choose the depth of discovery.** For a clear, small request, work directly. For consequential uncertainty, use a locally maintained repo-aware grilling entry point that consults the pinned `grilling` primitive. Ask the currently answerable decision frontier; find environmental facts yourself; let the user make the decisions. Do not impose a fixed number of rounds on every task. A request to discuss or analyze stays read-only unless the user asks to save results.
2. **Capture only settled material.** When a durable artifact is warranted, save the outcome in the existing work README, adding `plan.md` only for substantial design. No mandatory plan file or separate save/build conversational approval. Confirm unresolved *decisions* with the user and honor normal tool permission prompts; do not treat an unanswered question as authorization to invent a decision. A user request to implement can proceed once the intent is clear, subject to tool permissions and other safeguards.
3. **Synthesize a spec only when it helps.** A locally adapted `to-spec` consumes the discussion and codebase evidence without restarting the interview. For small work, summarize the contract in the work README. For a multi-session build or a substantial behavioral contract, write a linked `spec.md`; use bounded stories, current/desired behavior, out-of-scope, testing seams, and uncertainties rather than upstream's requirement for an extremely long story list. No automatic issue publication, `ready-for-agent` label, or duplicate acceptance checkboxes.
4. **Slice only when needed.** First try a checklist of independently verifiable vertical slices in the work README. Note genuine `Blocked by` relationships where order matters. When an effort needs independently owned records, separate work folders can be linked under the parent, with one writer per checkout and shared-index reconciliation by the coordinator. Do not assume that Matt's one-file-per-ticket local tracker is necessary. A later `to-tickets` decision must use an actual effort to test whether this simpler structure is insufficient.
5. **Build and deliver under the existing rules.** Existing validation, reviewers, [`commit-message-writer`](../../../skills/commit-message-writer/SKILL.md), [`changelog-writer`](../../../skills/changelog-writer/SKILL.md), `ship`, and todo closeout retain their authority. Keep `ship`'s developed PR narrative: behavior, motivation, decisions, actual checks, and limitations. Add a relevant screenshot for a visual change when capture is possible; use a small code or output excerpt, diff sketch, file or call tree, or Mermaid diagram when it explains a change better than prose alone. Put each visual beside the point it supports, not in a required template. Show before/after evidence only when it is real and useful; label illustrative pseudocode and never invent test output. Use PR-hosted attachments or link durable evidence already in the work record's `assets/`; do not create another PR-assets directory. Check images and excerpts for secrets, personal data, and internal URLs before publishing. No upstream implementation skill may commit to the current branch, close a task, delete artifacts, or push around those rules.

Retiring `planning-first` means removing its mandatory two rounds and its separate save/build conversational approvals from the applicable agent instructions and prompt routing. **It does not disable Pi's permission-gate prompts**, override a requested read-only mode, waive human decisions during grilling, permit secret-file reads, authorize unapproved file deletion, or remove `ship`'s confirmation before a direct push to `main`. Until the future migration is implemented, the existing instructions still apply.

## Trial and decision order

1. **Confirm the artifact contract.** Review this proposal against the Skills repository and a representative project with different existing docs. Agree on one domain-doc pointer and one work-record owner per repo. This is a design gate, not a mandatory conversational round for every future task. Do not change current instructions yet.
2. **Try grilling first.** Register and verify only upstream `grilling` at a reviewed commit, as an ignored generated skill through `tracked-skills`. Invoke it explicitly on one real, bounded uncertainty. Keep the conversation read-only or capture settled work in the existing README under the current rules. Compare question dependencies, user effort, unresolved decisions, and whether its final confirmation is useful. Do not install the wrappers or run upstream setup.
3. **Build the local entry point.** If the trial helps, create an original, cross-agent repo-aware grilling skill with the file contract above and retire `planning-first` and `/plan` routing together. Update the applicable Skills and Dotfiles/Pi instructions and their tests in a separately authorized implementation. A request to implement should not require two preset rounds, a mandatory plan file, or another conversational go-ahead once the task is clear. Keep existing tool and shipping safety boundaries.
4. **Try spec synthesis.** Use one substantial effort to decide whether the agreement fits its README or needs `spec.md`. Adapt `to-spec` only if it improves transfer to a fresh session. Verify terminology, scope, acceptance, and testing decisions without duplicating checkboxes or publishing to issues.
5. **Try domain modeling.** On a real terminology or architectural disagreement, compare the code and current docs, then create or update the canonical glossary or an ADR only if the thresholds are met. Validate that a future agent can find it through the project entry point without loading old work wholesale.
6. **Evaluate tickets last.** Choose an effort whose slices really can be delivered separately. Attempt the workbench's checklist plus blocker links first. Consider per-slice records or tracker links only if the simpler representation fails on ownership, discoverability, or dependencies. Explicitly decide whether `to-tickets` is worth maintaining as a local skill.
7. **Improve PR presentation within `ship`.** On a suitable visual or architectural PR, keep the existing detailed description and add only the screenshots, excerpts, or diagrams that help a reviewer understand or verify the change. Confirm attachment safety, source accuracy, and whether the additions improve review without obscuring motivation or limitations.
8. **Expand selectively.** Test optional reference, review, testing, and debugging skills against the established contract one at a time. Never import the entire suite as one migration.

Success is observable when a fresh agent can find the current priority, work contract, domain language, and relevant decision without choosing between two trackers or executing a historical plan; an interactive grill resolves dependent decisions without fixed rounds; a subsequent implementation uses existing Git safety and closeout. Failed trials should be reversible by removing an external pin, not by migrating project files back.

## Cross-agent and safety constraints

- Keep maintained skill behavior in portable `SKILL.md` and short project entry-point pointers. Treat `disable-model-invocation`, tool names, slash commands, and automatic skill composition as harness-specific until tested. Pinning upstream text does not imply it can be invoked unchanged in every agent.
- Use a single configured skill source across agents where possible, but validate retrieval and the destination path in Pi, Hermes Agent, Zed, Codex, and Claude Code before claiming parity. Avoid duplicate installed skill names or two different versions claiming the same trigger.
- Keep the parent as the only subagent orchestrator, with separate worktrees for concurrent writers. A pinned instruction to spawn an agent cannot grant a child permission to spawn more agents.
- Keep secrets unread, including `.env*` outside the allowed schema exception. Do not let a research, debugging, setup, or wizard skill weaken that constraint. Public-repo checks, approval for file deletions, and confirmation before a direct push to `main` stay in force.
- Preserve the upstream license and attribution for pinned or substantially copied material. Locally maintained adaptations should use independent wording and structure, with an attribution link for inspiration. Review upstream changes deliberately rather than auto-updating the operating procedure.

## Alternatives not selected

- **Pin everything, then reconcile files afterward:** fastest to install, but several skills write to an issue tracker, root glossary, or `.scratch/`. The divergent artifacts are harder to unwind than a small up-front path contract.
- **Replace `todo/` with Matt's issue tracker:** better native dependencies for issue-heavy teams, but loses the stable local work records, priority semantics, reviewed closeout, and portable Git-centered history that are already useful here.
- **Rewrite every upstream skill immediately:** one consistent voice but large maintenance burden before knowing which ideas work in practice. Pin the independent primitive first, then maintain only the integration seams that prove necessary.
- **Keep mandatory `planning-first` alongside grilling:** creates two competing interview and approval methods. Retire it as a behavior and update all references together when the replacement is ready, rather than leaving both active.

## Open questions for implementation trials

- Does direct use of `grilling` feel appropriately paced, or does its instruction to exhaust the decision frontier ask too much for routine work?
- Which existing projects already have a domain glossary or ADR convention that the local adapter must respect instead of the proposed default paths?
- Will the work README and optional `spec.md` suffice for a genuine multi-slice effort, or is a separate dependency-aware ticket surface worth its upkeep?
- Which agents discover the shared pinned `grilling` skill automatically, and which need an explicit routing pointer or a different invocation convention?

No question here blocks saving this proposal. The trials answer them before the corresponding workflow is activated.
