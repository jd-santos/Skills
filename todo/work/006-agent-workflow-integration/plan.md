# Agreed implementation plan: discovery with one workbench

This plan records the decisions from an interactive grilling trial and the implementation contract. The [work README](README.md) owns current status and the execution checklist. The reviewed `grilling` commit is registered, installed, and verified; live interaction and cross-agent retrieval remain untested. The mandatory `planning-first` skill and Pi's `/plan` prompt have been retired.

## Problem and decision

The retired `planning-first` skill forced two question rounds and separate permission to save a plan and to build. That structure is too rigid for the user's current workflow. Matt Pocock's [grilling](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/productivity/grilling/SKILL.md) explores a dependent decision tree more effectively, while his [domain modeling](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/domain-modeling/SKILL.md) separates enduring terms and decisions from task notes. His engineering flow assumes an issue tracker, root `CONTEXT.md`, `docs/adr/`, and in places a `Skill` tool or automatic commits. Adopting that flow unchanged would undermine the existing workbench and delivery rules.

**Agreed direction:** Keep [`todo-manager`](../../../skills/todo-manager/SKILL.md) and [`ship`](../../../skills/ship/SKILL.md) as the lifecycle backbone. Pin upstream `grilling` unchanged at the reviewed commit after source and license review. Build a small, portable router skill for choosing the shortest useful process, including grilling paired with a locally adapted domain-modeling skill when the domain itself needs clarification. Adapt spec synthesis only when useful, and defer `to-tickets` until a real multi-slice trial. Design a future route for Wayfinder without adopting it yet. Borrow useful visual evidence from the upstream `pr` skill inside `ship`'s existing PR-writing flow.

The artifact contract and conversation trial come before installation. Do not create an issue tracker, glossary, ADR directory, spec file, or ticket directory merely to make a skill happy.

## Artifact contract

The paths below are defaults for a project that already uses this workbench or explicitly adopts it. Existing authoritative docs and legacy task locations take precedence until a separate migration is authorized. Create optional files only when their content exists. A repo may use a different established documentation path, recorded once in its agent entry point; adapters must follow it rather than silently building this layout alongside it.

In this workbench, number effort folders in creation order as `todo/work/NNN-descriptive-name/`, beginning at `001`. The prefix is a stable browsing aid, not priority, status, or a revision number. Do not renumber after reprioritizing or completing work, and do not reuse gaps. Backfill the six existing efforts by their first Git addition, then assign the next number to each new work record. This is a deliberate migration of this workbench, not permission to rename records in other projects.

| Artifact | Owner and purpose | Not for |
| --- | --- | --- |
| `AGENTS.md` or the existing agent entry point | Short, cross-agent pointer to the live task queue, domain glossary, decisions, and applicable skills; project-specific constraints | A second task list, glossary, or transcript |
| `todo/TODO.md` | One live P1–P5 priority index; links substantial work records | Triage state labels, full specs, detailed duplicate checklists |
| `todo/work/<NNN-effort>/README.md` | Stable record for purpose, status, ownership, concise acceptance criteria, one detailed execution checklist, provisional domain findings, effort-specific decisions, and links | Claiming proposed behavior is already delivered, or becoming a second changelog |
| `todo/work/<NNN-effort>/plan.md` | Optional current design and consequential alternatives when they no longer fit in the README | Another execution checklist or a general project manual |
| `todo/work/<NNN-effort>/spec.md` | Optional detailed behavior, scenarios, edge cases, testing approach, relevant decisions, and open contract questions for a substantial or multi-session build | A required file for small work, duplicate acceptance checkboxes, status, or an automatic GitHub issue |
| `todo/work/<NNN-effort>/research.md`, `validation.md`, `assets/` | Evidence when useful, linked from the work README | Automatic per-session output or unlinked scratch |
| Existing maintained domain docs, or `docs/domain/README.md` only when needed | Shared, verified or adopted vocabulary; a dedicated glossary exists only when several reusable terms need one place | Tentative terms, implementation steps, task status, acceptance criteria |
| `docs/domain/<context>.md` | Optional glossary for a genuine bounded context when one glossary stops being usable; indexed by the glossary entry point | One file per feature or per work record |
| `docs/adr/NNNN-<decision>.md` or the existing decision convention | Rare, consequential, agreed domain or architectural tradeoffs; links the originating work record and clearly distinguishes decisions from implemented behavior | Every local implementation choice, basic term definition, or copied plan history |
| Existing maintained project docs | Current operational and architectural reference, separate from work history | Replacing the task index |
| `CHANGELOG.md`, Git, PRs, `todo/DONE.md` | Release notes, verified delivery/history, and navigation, respectively | Claims inferred from a checked task |

Use existing maintained documentation for shared vocabulary. If several settled terms need one home and no glossary exists, create `docs/domain/README.md`; a single-domain project needs no further context tree. Respect an existing `CONTEXT.md`, glossary, or ADR convention rather than adding a second one. `docs/adr/` is a lazy default for a qualifying decision, not a request to relocate old decisions. A repository without a task workbench keeps its existing tracker until it explicitly adopts or migrates one.

**One source of truth at each resolution:** The work README owns status, the authoritative execution checklist, and concise acceptance criteria. Its linked plan or research records working terms, code contradictions, and the reasoning accumulated during the effort. A spec elaborates detailed behavior, scenarios, edge cases, testing decisions, scope, and unresolved contract questions. It links the README criteria instead of copying their checkboxes or defining another workflow state. An ADR owns the distilled, durable decision and links the originating work record; the work record links back instead of copying the ADR's authority. A glossary defines shared terms; an ADR explains a choice; a plan describes proposed work. Old work records remain evidence, not standing instructions.

**Promotion rule:** During an authorized development session, capture settled *working* decisions in the work record as they crystallize; do not automatically commit each update. For a substantial, project-specific deliverable, including an answer-only one, check whether it belongs in the project's established backlog even without an explicit TODO request. Pure exploration, unrelated questions, and requested read-only sessions do not authorize task writes. Promote vocabulary to existing maintained docs only when adopted or verified beyond the effort, adding a dedicated glossary only when several shared terms justify it. Offer an ADR for a major domain or architectural choice only when it is hard to reverse, surprising without context, and a real tradeoff. An agreed decision that other work needs may enter `docs/adr/` before implementation if its status and future-facing nature are explicit; otherwise add it alongside the change it explains. Neither an ADR nor a glossary may claim proposed behavior is already shipped. The agent entry point should point agents to relevant current domain docs and decisions when planning, naming, testing, or reviewing that domain.

**Git history:** Updating a work record during a grill is not a request to commit every answer. `ship` groups ready work by intent: commit an independently useful decision on its own, or commit its ADR and current-behavior docs with the corresponding implementation. Keep the work record as linked context, not duplicate prose in each artifact, and carry consequential reasoning into the commit body. Clearly label pre-implementation plans and decisions. Never create automatic commits from a discovery or documentation skill.

### Example, not scaffolding to create now

```text
AGENTS.md
CHANGELOG.md
docs/
  domain/README.md             # only if several shared terms need a glossary
  adr/0001-<decision>.md       # only after a qualifying, agreed decision
todo/
  README.md
  TODO.md
  DONE.md
  work/NNN-example-effort/
    README.md                  # the effort's entry point and only checklist
    plan.md                    # if design needs room
    spec.md                    # if a durable behavioral contract needs room
```

No `.scratch/<feature>/issues/` tree, parallel `docs/agents/issue-tracker.md`, root `CONTEXT.md`, or hosted issues are created by the default hybrid. If a repo already uses hosted issues, an issue URL can be linked from the work README. Decide explicitly which location owns status and acceptance criteria before mirroring anything across systems.

## Process contract

1. **Route to the smallest useful process.** The maintained cross-agent router is a skill, not a Pi tool or a required step for every task. People normally invoke it; an agent may suggest it when an effort appears large enough. Up front, recommend direct work or chat-only discussion, an inline TODO item or one work record, grilling, grilling paired with domain modeling, optional spec synthesis, or later implementation slicing. Follow explicit user direction; ask only if the route remains unclear after examining the task and repository. Recommend the shortest useful sequence, not every skill in order. Name an unavailable recommended skill and ask before substituting. Do not assume a particular host's `Skill` tool or command syntax.
2. **Grill only when decisions need it.** Use the unchanged, pinned `grilling` discipline for consequential uncertainty. Investigate environmental facts yourself, ask the answerable decision frontier with recommendations, and let the user decide. Pair it with locally adapted domain modeling when terms, relationships, or boundaries need clarification. Challenge ambiguous vocabulary against code and existing docs and test it with concrete scenarios, but capture working findings in the work record, not directly in a new root `CONTEXT.md`. Ordinary planning grills do not require domain modeling. After grilling, confirm shared understanding once; then carry out the next step already requested, subject to normal tool permissions and safety rules. Pure exploration stays read-only unless the user asks to save results; check separately whether a substantial project-fit answer-only deliverable belongs in the established backlog.
3. **Capture only settled material.** On an authorized write, put effort-specific outcomes in the existing work README, adding `plan.md` only when substantial design needs room. A substantial project-fit answer-only request may also merit a task record even without the word TODO; check whether it belongs to the project's backlog first. Do not require preset question rounds, a plan file for every task, or separate conversational approvals to save and build. Do not infer an unanswered decision or permission to write from a suggested route. Follow the promotion and Git-history rules above for domain documentation.
4. **Synthesize a spec only when it helps.** A locally adapted `to-spec` consumes the discussion, maintained docs, and codebase evidence without restarting the interview. The user may request it, or an agent may suggest it when a project-fit behavioral contract needs to survive across sessions. For small work, summarize the contract in the work README. For substantial or multi-session behavior, write a linked `spec.md` in the numbered effort folder. Keep stories optional and bounded; use scenarios when they clarify behavior. Inspect existing test seams and prefer observable behavior, but ask the user about a seam only when the choice materially changes scope, cost, or confidence. Surface contradictions between conversation, code, and maintained docs before treating the contract as agreed; record non-blocking unknowns openly. The README owns concise acceptance criteria, the checklist, and status. Producing a spec does not itself authorize implementation or require a second approval for implementation already requested. No automatic issue publication, `ready-for-agent` label, or duplicate acceptance checkboxes.
5. **Slice only when needed.** A future locally adapted `to-tickets` should consume an agreed spec, plan, or conversation and propose independently verifiable vertical slices with real `Blocked by` edges. First try one checklist in the effort README, with a brief delivery outcome and blockers per slice. Split into separately linked numbered work records under `todo/work/` when the checklist becomes hard to parse as a backlog or independent ownership and delivery require it, not merely because upstream expects a file per ticket. Preserve the upstream wide-refactor exception through expand–contract steps when vertical slices cannot stay green. Check granularity and blockers with the user when the breakdown is consequential. Trial this on a real multi-slice effort before maintaining a `to-tickets` skill; do not introduce a second issue tracker, triage label, or duplicate acceptance lists.
6. **Reserve Wayfinder for a later trial.** The router may identify an effort too large and uncertain for one session and suggest that the user consider Wayfinder, but human instruction normally chooses that route. A future adapted Wayfinder would map decisions first, then hand a clarified destination to spec or slicing when useful; it must not create another tracker by default. Do not claim the upstream skill works with this workbench or automatically invoke it now.
7. **Build and deliver under the existing rules.** Existing validation, reviewers, [`commit-message-writer`](../../../skills/commit-message-writer/SKILL.md), [`changelog-writer`](../../../skills/changelog-writer/SKILL.md), `ship`, and todo closeout retain their authority. Keep `ship`'s developed PR narrative: behavior, motivation, decisions, actual checks, and limitations. Add a relevant screenshot for a visual change when capture is possible; use a small code or output excerpt, diff sketch, file or call tree, or Mermaid diagram when it explains a change better than prose alone. Put each visual beside the point it supports, not in a required template. Show before/after evidence only when it is real and useful; label illustrative pseudocode and never invent test output. Use PR-hosted attachments or link durable evidence already in the work record's `assets/`; do not create another PR-assets directory. Check images and excerpts for secrets, personal data, and internal URLs before publishing. No upstream implementation skill may commit to the current branch, close a task, delete artifacts, or push around those rules.

The `planning-first` retirement removes the standalone skill, its mandatory two rounds, and its separate save/build conversational approvals from applicable agent instructions. Pi's `/plan` template and current-feature references are removed rather than replaced with another Pi-specific command. **It does not disable Pi's permission-gate prompts**, override a requested read-only mode, waive the final confirmation in a grill, permit secret-file reads, authorize unapproved file deletion, or remove `ship`'s confirmation before a direct push to `main`. The shared router now supplies the optional route without adding another permission gate.

## Trial and decision order

1. **Confirm the artifact contract.** The conversation trial agreed on one work-record owner, selective promotion into maintained docs, and a portable router. Before activating it in another repository, inspect that project's existing task and domain-doc conventions; do not silently migrate them or change current instructions yet.
2. **Pin and trial grilling.** The exact source and MIT license were reviewed, and the `grilling` pin was registered, installed, and verified as ignored generated content. A live interaction trial remains: use it on a bounded uncertainty, then compare question dependencies, user effort, and handoff into the existing work record against the conversation trial below. Do not install its wrappers or run upstream setup.
3. **Build the local router skill.** The original cross-agent `work-routing` skill and focused routing checks are implemented in the Skills checkout. The user authorized implementation. The `planning-first` retirement, removal of Pi's `/plan` template and current-feature references, and Pi instruction changes are a separate Dotfiles change from the first Skills delivery.
4. **Build and trial spec synthesis.** The locally maintained [`to-spec`](../../../skills/to-spec/SKILL.md) uses independent wording and attribution after the saved design and compaction checkpoint. Focused tests cover routing into the authoritative work record and optional `spec.md`, nonredundant README criteria, contradictions, flexible scenarios, and meaningful testing seams. Trial it on a real behavior contract; do not claim live success merely because the skill file exists.
5. **Try domain modeling.** On a real terminology or architectural disagreement, compare code and current docs while capturing working findings in `todo/`. Test selective promotion into existing maintained docs; create a glossary only for several shared terms, or an ADR for a consequential agreed choice. Validate that a future agent can find the result through the project entry point without loading old work wholesale. Until this adaptation exists, the router must not invoke the upstream skill as a writer.
6. **Evaluate tickets later.** Choose an effort whose slices really can be delivered separately. Attempt a readable work README checklist with blocker links first. Split into numbered records under `todo/work/` if backlog readability or independent ownership and delivery require it. Verify granularity, true blockers, and the wide-refactor exception before deciding whether `to-tickets` deserves its own local skill. No `.scratch/` files or hosted issues by default.
7. **Improve PR presentation within `ship`.** On a suitable visual or architectural PR, keep the existing detailed description and add only the screenshots, excerpts, or diagrams that help a reviewer understand or verify the change. Confirm attachment safety, source accuracy, and whether the additions improve review without obscuring motivation or limitations.
8. **Expand selectively.** Test optional reference, review, testing, and debugging skills against the established contract one at a time. Never import the entire suite as one migration.

The conversation trial exposed a useful failure mode: looking only for installed skills missed the external skills linked from the work record. Once the reviewed `grilling` instructions were used, dependent questions found the router, documentation, and Git-history decisions without preset rounds. The first proposed artifact contract was too eager to publish a glossary; the domain-modeling conflict was resolved by keeping working notes in `todo/` and promoting only selected enduring outcomes. This is evidence for a local routing and artifact seam. The installation is now verified at the selected commit, but the live interactive trial and cross-agent retrieval remain untested.

Success is observable when a fresh agent can find the current priority, work contract, domain language, and relevant decision without choosing between two trackers or executing a historical plan; an interactive grill resolves dependent decisions without fixed rounds; subsequent implementation uses existing Git safety and closeout, and history contains coherent changes rather than a commit per question. Failed trials should be reversible by removing an external pin, not by migrating project files back.

## Cross-agent and safety constraints

- Keep maintained skill behavior in portable `SKILL.md` and short project entry-point pointers. Treat `disable-model-invocation`, tool names, slash commands, and automatic skill composition as harness-specific until tested. Pinning upstream text does not imply it can be invoked unchanged in every agent.
- Use a single configured skill source across agents where possible, but validate retrieval and the destination path in Pi, Hermes Agent, Zed, Codex, and Claude Code before claiming parity. Avoid duplicate installed skill names or two different versions claiming the same trigger.
- Keep the parent as the only subagent orchestrator, with separate worktrees for concurrent writers. A pinned instruction to spawn an agent cannot grant a child permission to spawn more agents.
- Keep secrets unread, including `.env*` outside the allowed schema exception. Do not let a research, debugging, setup, or wizard skill weaken that constraint. Public-repo checks, approval for file deletions, and confirmation before a direct push to `main` stay in force.
- Preserve the upstream license and attribution for pinned or substantially copied material. Locally maintained adaptations should use independent wording and structure, with an attribution link for inspiration. Review upstream changes deliberately rather than auto-updating the operating procedure.

## Alternatives not selected

- **Pin everything, then reconcile files afterward:** fastest to install, but several skills write to an issue tracker, root glossary, or `.scratch/`. The divergent artifacts are harder to unwind than a small up-front path contract.
- **Replace `todo/` with Matt's issue tracker:** better native dependencies for issue-heavy teams, but loses the stable local work records, priority semantics, reviewed closeout, and portable Git-centered history that are already useful here.
- **Rewrite every upstream skill immediately:** one consistent voice but large maintenance burden before knowing which ideas work in practice. Pin the independent primitive first, then maintain only the integration seams that prove necessary.
- **Keep mandatory `planning-first` alongside grilling:** creates two competing interview and approval methods. Retire it as a behavior and update all references together when the replacement is ready, rather than leaving both active.
- **Write every resolved term directly into a new glossary and commit as you go:** makes tentative work look canonical and fragments Git history. Capture working material in the work record and promote selectively.
- **Keep Pi's `/plan` as a router:** adds a host-specific route without unique behavior. Use one portable skill; remove the template.

## Open questions for implementation trials

- Does the installed `grilling` skill keep the useful dependent-question flow without over-questioning routine work?
- Which existing projects already have domain docs or ADR conventions that the adapter must respect instead of the proposed defaults?
- Will the work README and optional `spec.md` suffice for a genuine multi-slice effort, or will independent numbered records under `todo/work/` improve readability, ownership, and dependencies enough to justify them?
- Which agents discover the shared pinned `grilling` skill and router, and which need a short project entry-point pointer?

These questions are validation targets for the implementation trials, not reasons to create speculative documentation now.
